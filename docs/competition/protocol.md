# 通信仕様と動作確認用サーバー

確認日：2026-09-21。出典は[8月20日の公式公開資料](https://www.procon.gr.jp/news/2026/08/20/117)（API）。
配布ZIP内の `回答システムに関する情報.zip/redoc-static.html`（Procon 37 API 0.0.0）、
`簡易サーバー.zip/README.md`、`試合設定用JSONファイル.zip/試合設定JSONについて.md` を確認した。
本番の進行は[9月18日の本選条件](finals-conditions.md)と併読する。

## HTTPと認証

HTTP/1.1を使い、リクエストは秒間5回程度を目安とする（Q41・Q42）。
公開APIは全操作にヘッダー `Procon-Token` とクエリ `token` を定義する。
両方はスキーマ上optionalだが、認証不要を意味しない。401 `AuthError` が定義されている。
運用ではヘッダー方式を基本とし、両方指定時の優先順位や無指定時の詳細は未確認とする。
本番のホスト・ポート・自チームトークンは当日の案内を用い、配布例から推定しない。

| メソッド・パス | 入力 | 成功応答 |
|---|---|---|
| `GET /setting` | 認証情報 | `MatchSetting`（マップ・日程等） |
| `POST /agent` | 車両数と同じ長さの0/1配列 | 200。応答本文のスキーマは未定義 |
| `GET /` | 認証情報 | `MatchState`（当日開始状態） |
| `POST /` | 全車両の行動列を含む整数二次元配列 | `{ "revision": 整数 }` |

各操作に401 `{code:"AuthError", message:...}` と403 `{code:"AccessTimeError", message:...}` が定義される。
403の説明は試合設定前・終了後のアクセス。すべての不正入力やフェーズ違反の応答が網羅されているとはみなさない。
503の開始待ちでの意味は公開仕様から未確認。管理用の `official.poll_start: true` は、
初回設定取得・開始待ちのGETが503なら1秒後に再取得する実装方針とする。
通常のGETと行動・種別POSTは、通信失敗またはHTTP 500/502/503/504で
`official.retry_count` 回まで再試行する。初回を除く0以上の整数で、既定2（初回込み最大3回）。
0で再試行を無効にでき、4なら初回込み最大5回。指定できる上限は2147483646。
再試行は0.5秒待ち、停止要求・既知の締切・260ms以上の通信間隔を守る。401/403や不受理のrevisionは再送対象にしない。
行動POSTは応答JSON不正・revision欠落も再送対象とし、毎回直前にGETでdayとendsAtを照合する。
日別の送信余裕を残した締切までに受理が確認できなければ、履歴を確定せず停止する。
種別POSTは同じ編成を再送し、既知の種別締切を越えない。poll_startでは種別締切を推測せず設定回数で打ち切る。
開始待ちの503・403 AccessTimeErrorに対する1秒ポーリングは、この再試行回数の対象外。
`official.state_read_recovery_seconds` は翌日以降の `waiting_day`、
既知の対象日・`endsAt`を照合する提出前GET、明示車種締切が既知の初期setting GETの追加復旧枠。
既定0で従来の回数制限を保ち、`retry_count=0` でも無効となる。有限の非負秒数で、
単調時計の範囲に収まる値を指定する（自動参加の候補値は30秒、採用と実戦確認は別途）。
翌日の一連の状態取得、1回の提出前確認GET、または初期setting取得の開始時に一度だけ固定し、
物理GETの再試行・古い状態・503待機で再開始しない。
提出前は初日にも既知の状態があるので対象とし、取得したday/endsAtの整数契約と一致を確認する。
取得上限は固定単調上限と `endsAt - submit_margin_seconds - 0.3` の短い方で、
既存のPOST直前0.3秒余裕を越えたfresh応答も採用しない。
POST後に同じ回答を再送する際の確認GETは別の論理GETだが、同じ既知の公式締切を守る。
初期settingは `poll_start=false` で `type_deadline_unix` が明示されている場合だけ対象とし、
固定単調上限と `type_deadline_unix - submit_margin_seconds` の短い方を守る。
取得待ちも車種計算の予算へ含め、車種期限やselection_started_atを延ばさない。
未知締切の初日開始待ち、その他の通常GET、種別POST、行動POSTの再送回数・本文・受理確定契約は変更しない。
接続・読み書き・SSL接続の過渡失敗とHTTP 500/502/503/504のGETだけを追加復旧し、
壊れたJSON・認証・証明書/ホスト名検証・状態の契約違反は追加復旧しない。
GETの証明書読み込み・証明書/ホスト名検証失敗は通常の回数再試行もせず停止する。
GETの通信失敗ログは固定enum名・SSL/OpenSSL数値・単調elapsed・設定timeoutのみを追加し、
HTTP応答なしは `http_status: null` とする。トークン・ヘッダー・URL全体は追加しない。
翌日の状態取得は、固定したローカル取得上限と、
確認済み対象日の `endsAt - submit_margin_seconds` の短い方で要求と待機を制限する。取得したdayが期待日より先なら停止し、古い状態からは探索しない。
未取得の日のローカル上限を公式期限とは断定せず、枯渇時は `state acquisition budget expired` と記録する。
単発DNS/TLS呼出しの終了が指定timeoutを超える可能性は残るため、戻った直後も上限を再確認し、
遅い応答から探索・POST・受理履歴の追加を始めない。
設定・停止条件は[UI操作説明書](../development/ui-manual.md#4-guiで開始し進行を確認する)を参照。
送信JSONの意味と合法性は[形式](../rules/06_formats.md)を参照。JSONの本文を扱う操作は `application/json`。

## 設定と状態

- `MatchSetting`：`startsAt`、`daySeconds`、`daySteps`、`map`、`spots`、`agents`、`fuelLimits`、`players`、`busyThreshold`、`jammedThreshold`。
- `startsAt` はUNIX TIMEの開始時刻。確定前は0。`agents` は自チームの初期位置の整数配列。
- `MatchState`：`endsAt`、`day`、`agents`、`others`、`traffics`。`endsAt` は当日の受付終了UNIX TIME、初日は `day=0`。
- 状態の `agents` は `kind/pos/fuel`、`others` は他チームの `id/agents`、`traffics` は道路の `pos/status`。
- 獲得系列・玉数・過去の行動・道路の生の交通量は、この公開状態スキーマには含まれない。

タイプ受付終了後に初日が始まり、翌日以降も各日の受付開始時に前日終了状態を取得する（M p.2）。
`startsAt` をタイプ締切そのものと解釈する根拠や、タイプ受付の残時間取得方法は公開APIから確定できない。
管理用は、運用側で確認した待ち時間を `official.match_start_delay_seconds` に指定した場合に限り、
`startsAt − 待ち時間` を種別締切として扱える。これは設定に基づく実装上の解釈であり、
公式APIの締切保証ではない。`startsAt=0` は未確定として待機する。

## 受理と再提出

`POST /` の `revision` が負なら失敗、0以上なら受理。同じ日では値が大きい回答ほど後に受理されたものとなる。
HTTP 200だけを成功扱いしない。並列送信の応答到着順よりも `revision` を使って受理順を判断する。
制限時間内の再提出は可能で、最後の有効回答を採用する（G p.12）。大量送信は避ける。
最後に送った要求が不受理なら、それを採用回答とはみなさない。応答喪失時は受理の有無が未確定となる。
得点同点時の判定は、各日の**最後の有効回答までの回答時間の合計**が短い方を優先する（G p.12、Q56）。
早い初回提出の時間が残るのは、その後に有効な再提出をしなかった場合だけ。詳細は[勝敗判定](../rules/05_scoring.md)を参照。

有効な種別回答がなければ全車巡回、有効な行動回答がなければ全車待機（F p.3）。
通信再送の詳細、冪等性キー、種別回答のrevisionは公開仕様に定義されていない。
2026-10-06の公式簡易サーバーで、種別回答 `[0,1]` を2回、続けて `[1,0]` を送信した。
すべてHTTP 200・空本文で、初日状態のkindは最後の `[1,0]` と一致した。
これは配布macOS arm64バイナリでの縮小通信試験の観測であり、本番の挙動保証や本選統合検証ではない。
条件とバイナリハッシュは[再提出の確認記録](../experiments/168_official_resubmission.md)に残す。
履歴は受理された計画と実際の翌日状態を照合する必要があり、ローカルソルバの予測履歴を無条件で実績とみなさない。

### 実装側の運用方針

以下は公式仕様に基づいて選ぶ実装方針であり、公式が指定する探索方式ではない。

- 最初の合法回答ができたら保存して直ちに提出する。その後も、最終送信の余裕を除いた残時間まで探索を続ける。
- 同じ日の同じ評価条件で現在の最良候補を厳密に改善した、合法性確認済みの候補だけを再提出する。
- 同じ総合評価の候補では自動再提出せず、先に受理された回答を保つ。当日得点が同じでも将来の改善を見込む候補は、総合評価の根拠を記録して比較する。
- 受理不明・失敗からの復旧再送は改善時の再提出と分けて判断する。有効に再受理されれば判定時間が更新され得る。
- 送信を原則直列にして候補ID・日付・非負の `revision` を対応づける。古い候補を後から送らない。
- 検証・保存・通信・受理確認・再試行と時計の不確かさを見込んで探索を止める。最終送信余裕は実測して設定し、締切ちょうどの送信を目標にしない。

この逐次改善運用は今後の試合管理の要件。ローカル診断試験の進行と観測結果は[通信実験](server-experiments.md)で分けて管理する。

## 簡易サーバーの起動手順

配布ZIPを展開し、OSに合ったバイナリと設定ZIPの `example.json` を用意する。
以下は同梱READMEに基づくローカル動作確認例。個別の実行結果は通信実験の記録を参照する。

```bash
# 配布ファイルを置いたディレクトリで実行（macOS Apple Silicon）
chmod +x procon-server-darwin-arm64
./procon-server-darwin-arm64 -config example.json -addr 127.0.0.1:8080
```

Linuxは `procon-server-linux-amd64`、Intel Macは `procon-server-darwin-amd64`、Windowsは `procon-server-windows-amd64.exe`。
`-config` は必須。`-addr` の既定は環境変数 `PORT`、未設定なら `:8080`。
`-kind-deadline` は起動から種別締切まで（既定5s）、`-match-start-delay` は種別締切から試合開始まで（既定5s）。
起動後は自動進行する。この既定値や開始待ちを本番の時間配分と同一視しない。

設定JSONのトップレベルは `problem` と `teams`。チーム要素は必須の `token` と任意の `name`。
`problem` は `width/height/cells/spots/agentStarts/fuelLimits/daySteps/daySeconds/busyThreshold/jammedThreshold`。
これは `GET /setting` の応答とは異なる形式で、solverのMAP引数へ直接渡すものではない。

## 確認できた範囲と残課題

配布物はAPI HTML、OS別バイナリ、README・クレジット、設定説明・例。
確認したZIPにサーバーソースコードは含まれていない。資料の確認と、個別の実験で観測したバイナリの挙動は区別する。
認証、startsAt=0、無効JSON、未回答、再提出、日替わり、補給の縮小ケースを観測した。
無効行動・壊れたJSONはHTTP 200・revision=-1、種別不正はHTTP 400だった。これは簡易サーバーの観測であり全実装の応答保証ではない。
同じステップ数の翌日に前日用の合法回答を送ると、翌日の回答として受理されることも確認した。対象日はクライアントが管理する。
厳密な受付瞬間、認証方式の競合、通信切断後の復旧、本番での挙動は未確認。
現行リポジトリとの対応と不足は[実装対応表](../development/implementation-status.md)に集約する。

配布物のダウンロードリンク・保存先・Git除外と次の検証は[通信実験計画](server-experiments.md)を参照。
