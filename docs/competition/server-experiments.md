## ローカル配置

すべて競技リポジトリのルートからの相対パス。

```text
2026-kyogi/
  .local/                           # 全体をGit管理対象外にする
    official-server/
      downloads/                    # 元ZIPと取得情報
      bin/                          # OS別実行ファイル
      config/                       # example.jsonと試験用設定（トークンを含む）
      reference/                    # API HTML、README、クレジット、設定説明
    competition/
      secrets/                      # 接続先・トークンなどの個別設定
      runs/<run-id>/                # 通信ログ、元応答、計画、履歴、再生用データ
```

Apple Silicon用は `.local/official-server/bin/procon-server-darwin-arm64`。
Linux用・Intel Mac用・Windows用も同じ `bin/` 配下に配布時の名前で置く。
移行前のビジュアライザ側の配置は過去実験用。現行の実行元は競技リポジトリへ統一する。保存先はリポジトリ内だが `.local/` 全体を `.gitignore` で除外する。
コミットするのは実験コード、秘匿情報を含まない小さな自作fixture、手順、匿名化・要約した結果のみ。
配布設定のトークン、本番トークン、生のヘッダーやURLを成果物へ混入させない。共有ログは認証情報を伏せる。

## 実験の段階

| ID | 実験 | 確認すること | 完了条件 |
|---|---|---|---|
| S0 | 起動と認証 | localhostへのバインド、設定形式、正しい／誤った／欠けたトークン | 再現可能な起動手順と設定取得・認証エラーの記録 |
| S1 | 最小の全日通信 | 全車巡回、全待機で種別から最終日まで進行 | 受付フェーズ、日付、endsAt、revision、翌日状態を対応づけたログ |
| S2 | 合法性と境界 | 不正な台数・方向・時間・燃料、再提出、未回答、日替わり・締切、燃料不足予約後の補給 | 期待・観測・相違を一覧化し、資料の記述と区別 |
| S3 | ソルバ接続 | 車種選択、日別計算、回答送信、採用計画の履歴 | 3区分で全日進行し、公式状態と計算結果を照合 |
| S4 | 異常系 | プロセス停止、遅延、応答喪失、再起動、GUI低速・非表示 | 二重進行や期限後送信を防ぎ、受理不明を表示・保存できる |
| S5 | 本番相当のリハーサル | M4・有線LAN・60秒回答、区分別タイプ時間、複数回 | 時間内の受理と復旧操作を確認し、使用版・手順を固定 |

S0～S2は最適化済みソルバがなくても始められる。S3以降は[担当と構成](../development/system-integration.md)に沿って実装する。
S0～S2では競技側の `scripts/probe_official_server.py` をローカル専用の観測用診断スクリプトとして使う。
小盤面の境界ケースは単体回帰用とし、本選の統合・性能検証の完了根拠にしない。
これは公式バイナリのブラックボックス試験であり、ソルバ実行・本番接続・締切までの探索を担当する製品用クライアントではない。
C++管理用をヘッドレスまたはUI接続で使用し、診断スクリプトを本番の第二の通信実装として運用しない。
故障・遅延の注入はローカルの簡易サーバーまたは模擬応答で行い、本番サーバーへ負荷試験をしない。

### 再提出と締切前の改善で確認すること

有効回答A、有効回答B、不正回答の順に送り、非負の `revision` と観測可能な翌日状態を記録する。
「最後に送った要求」ではなく「時間内に最後に受理された有効回答」が採用されることを切り分ける。
翌日状態だけで複数の候補を識別できない入力では、採用回答を断定しない。

本番方針は、最初の合法回答ができたら直ちに提出し、その後も改善を続け、検証済みの改善候補を再提出すること。
同じ総合評価の候補では自動再提出しない。当日得点が同じでも将来の改善を見込む候補は、評価根拠を記録して判断する。
[同点時の回答時間](../rules/05_scoring.md)は各日の最後の有効回答までの時間の合計であり、有効な再提出で更新される。受理不明・失敗からの復旧再送は別途判断する。
S0～S2の短い診断試験は探索性能を測らない。探索・候補通知・最終送信余裕の実測はS3～S5で行う。
締切ぎりぎりの送信成功を1回観測しても安全余裕を0秒にせず、遅延と再試行を含めて判断する。

## 結果の残し方

各runに入力のハッシュ、サーバーバイナリのハッシュ、クライアント・ソルバの版、起動設定、
壁時計と経過時間、対象日、提出候補ID、HTTPステータス、revision、標準出力・エラーを保存する。
HTTP 200、revisionによる受理、後から採用された回答の確定を別の事象として記録する。

C++・Rust・公式簡易サーバーで状態や得点が違う場合、どれかを無条件に正解とせず、最小の入力と公式根拠を添える。
公式APIで取得できない得点や最終結果は「未観測」とし、ローカル再生だけでサーバーとの一致を宣言しない。
試験ごとに「資料で確定」「簡易サーバーで観測」「本番未確認」を分ける。

新しい通信実験の報告は競技側の `docs/experiments/` に置く。移行前の報告は保存先を維持する。
C++ルール・解法の不具合や採否はソルバ側の実験記録へリンクする。生データは上記 `.local/competition/runs/` に置く。

## 別PC構成で追加する検証

本番は同じLANで相互通信するビジュアライザPCとソルバPCに分ける。Bの63項目はlocalhostでの競技API診断で、PC間連携の合格を意味しない。
S3ではJSONの遠隔受渡し・ジョブID・初回／改善候補・受理結果の引継ぎ、S4ではLAN遅延・切断・再接続・重複依頼・古い日の候補破棄・2台の時計差を検証する。
S5は両PCと本番用の配線で行い、候補転送も含む提出余裕を測定する。
