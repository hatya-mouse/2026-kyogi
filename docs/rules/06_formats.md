# JSON形式・提出条件

出典：F pp.1～3、Q3・Q9・Q12・Q19・Q26・Q39～Q42・Q47・Q53～Q57・Q61・Q62。
出典一覧は [資料一覧](../sources/08_sources_and_open_questions.md) を参照。

## 試合開始前のマップ構成

|キー|意味|
|---|---|
|`startsAt`|試合開始時刻、UNIX TIME|
|`daySeconds`|各日の回答時間、秒の配列|
|`daySteps`|各日の規定ステップ数の配列。要素数が日数|
|`map.height`, `map.width`|縦幅、横幅|
|`map.cells`|行ごとの地形コードの二次元配列|
|`spots`|スポットの配列|
|`spots[].brand`|整数の系列識別子|
|`spots[].pos`|スポットのセルID|
|`spots[].stocks`|最大在庫数。当日残在庫ではない|
|`agents`|自チーム各車両の初期セルIDの配列|
|`fuelLimits`|全巡回車に共通する燃料積載量上限|
|`players`|参加プレイヤー数|
|`busyThreshold`|混雑基準値|
|`jammedThreshold`|渋滞基準値|

`agents` の配列順が試合中の車両識別に使われる。
状態入力、種別回答、行動計画の全てでこの順を維持する。
同時獲得時の優先順位もこの順になる。

地形コードは0=平地、1=道路、2=山地、3=池。
`fuelLimits` は複数形のキー名だが、値は配列ではなく整数。

## 各日開始時の状態

|キー|意味|
|---|---|
|`endsAt`|今回の回答受付終了時刻、UNIX TIME|
|`day`|情報提供前の日付。初日が0|
|`agents`|自チームの車両状態の配列|
|`agents[].kind`|0=巡回車、1=補給車|
|`agents[].pos`|現在のセルID|
|`agents[].fuel`|現在の燃料量|
|`others`|他チームの情報の配列|
|`others[].id`|他チームのID|
|`others[].agents`|自チームと同形式の車両状態|
|`traffics`|道路セルの状態の配列|
|`traffics[].pos`|道路セルID|
|`traffics[].status`|0=順調、1=混雑、2=渋滞|

第1日の計画は `day=0` に対し `daySteps[0]` ステップ。
F p.2のサンプルに `day:1` とあるが、初日を1とする根拠にはしない。
入力の添字が配列範囲内か確認する。

道路の実交通量、他チームの行動履歴、獲得系列履歴はこの形式に含まれない。
初日にも車両状態が与えられる。翌日の位置・残燃料は配布された状態を使用する。

## 車両種別の回答

```json
[0, 1, 0, 1]
```

車両数と同じ要素数で、値は0または1。
要素数や種別が不正ならリジェクト。
締切までに有効な種別回答がなければ全車両が巡回車になる。

## 行動計画の回答

外側の配列が車両順、内側の整数配列がその車両の行動列。

|値|意味|
|---|---|
|0|左上に1セル移動|
|1|右上に1セル移動|
|2|右に1セル移動|
|3|右下に1セル移動|
|4|左下に1セル移動|
|5|左に1セル移動|
|-k（kは正の整数）|kステップ待機|

0は待機ではない。移動値は移動先セルIDでもなく、方向。
待機を生成するなら正の待機長を負号で符号化する。

例：1日16ステップ、3車両が全て待機する場合の有効な行動形式。

```json
[[-16], [-16], [-16]]
```

各車両について、移動元地形に応じた移動時間と待機時間の合計をNに厳密一致させる。
配列の要素数や移動回数がNという意味ではない。
1台でも不正な計画（ステップ数の過不足、池・マップ外への移動、燃料不足等）なら回答全体をリジェクト。
締切までに有効回答がなければ全台がNステップ待機する。

制限時間内は再提出でき、最後に受理された有効回答を採用する（G p.12）。
したがって後続の不正回答は、有効回答の採用対象を置き換えない。
回答の有効・無効は通知される。回答時間の順位判定には各日の最後の有効回答までの時間を使う（Q56）。

## 通信と時刻

- HTTP/1.1のみ対応（Q41）。
- リクエスト頻度は秒間5回程度を目安とする（Q42）。厳密な上限仕様としては示されていない。
- サーバー時計はNICTのNTPに同期（Q57）。
- 「1分程度」はQ4・Q5時点の想定。実際の回答時間は `daySeconds` と `endsAt` を使う。
- G p.12では有線LANとHTTP POST・GETでの送受信を予定している。
- パス・認証・HTTPメソッド・応答は8月20日の公開API資料で確認済み。[通信仕様](../competition/protocol.md)を参照。再送や境界挙動の未確認事項は同文書に残す。
- マップ情報更新には若干の遅延があり得る（G p.12）。

## サンプル値の注意

F p.1の `daySteps:[50,100,150,200]` と `fuelLimits:20` は
実際の燃料上限条件を満たさない。Q62で、初日50ステップなら上限50～150と明確化された。
サンプルは形式例であり、本番の整合した試合データとは限らない。
